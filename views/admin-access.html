Granting access to the demo

Sign-in is Google SSO restricted to an allowed email domain. There are two ways to let someone in: add them as an OAuth test user (the durable, recommended path), or create a username/password account in-app (quick, but wiped on the next deploy).

★ Invite someone by email No redeploy

Add an individual address here and this app will admit it at sign-in, even if the domain isn't on the allowed list — no GitHub variable edit and no redeploy. The invite is stored durably and survives restarts.

⚠️

One catch while the consent screen is in Testing mode: Google itself still blocks anyone who isn't a test user, and there is no API to add test users — it is console-only. So today an invite here must be paired with step 1. Publish the consent screen (step 1) and this box becomes the only thing you need.

1 Google sign-in Recommended · durable

The OAuth consent screen is in Testing mode, so only people on the test-user list can sign in — even if their email is on the allowed domain. Adding a user is a console-only click-through:

  1. Open the OAuth consent screen for the project.
  2. Under Audience → Test users, click + Add users.
  3. Enter their work email, then Save. (Limit: 100 test users.)
  4. Send them the app URL — they click Sign in with Google. No password needed.

Opening it to everyone on the domain

To stop maintaining the list, click Publish app on that same screen (Testing → In production). After that, anyone whose email is on an allowed domain can sign in without being listed individually.

2 Someone outside the allowed domain

Add their domain to ALLOWED_EMAIL_DOMAINS, then redeploy — these values are injected at deploy time, so a variable change only takes effect on the next deploy. 

gh variable set ALLOWED_EMAIL_DOMAINS -b "google.com,partner.com" -R UbhiTS/llm-compare
gh workflow run "Deploy to Cloud Run" -R UbhiTS/llm-compare

They still need to be a test user (or the app must be published).

⚠️

Don't add a broad consumer domain like gmail.com unless you genuinely want anyone with such an address to be able to run the demo on your API budget.

3 Making someone an admin

Admins see everyone's run history plus the usage dashboard, and are exempt from the daily run limit. Add their email to ADMIN_EMAILS (comma-separated) and redeploy: 

gh variable set ADMIN_EMAILS -b "you@example.com,them@example.com" -R UbhiTS/llm-compare
gh workflow run "Deploy to Cloud Run" -R UbhiTS/llm-compare

4 Username / password account Quick · temporary

For someone without an account on the allowed domain, or a one-off guest: open the user menu (top-right) → Manage users → add a username + password, optionally ticking admin. Share those credentials directly.

⚠️

These accounts do not survive a deploy. They live on the container's ephemeral disk, so every push to main (which redeploys) wipes them. The only durable password login is the break-glass admin, re-seeded on each start from the ADMIN_BOOTSTRAP_PASSWORD secret. For lasting access, use Google sign-in (option 1).
